## Context

**A race tick** runs every 53 ms on the game thread: the race's own step (physics, AI, collisions, and the drawing the original does as part of it), then, for the presenter, the run-ahead (the next tick played ahead and the race put back), the poses handed over (`handOverKept`), the kept scene recorded and made ready for the card. **The presenter thread** draws frames from the kept scene in between, placing the cars from the poses (`PoseSpan`).

**How it was measured.** A tick trace (`-Dnfm.framelog.csv=true`, `ticks-NN-part.csv`) gives each tick's due time, how late it began, its race step, the run-ahead, when the poses were handed over, the kept scene's recording and the card's part. A stack sampler (scratch tool, not shipped) gives the game thread's stack every few ms. Hidden runs (`-Dnfm.autotest`, 1920x1080, GPU renderer, the live test's seed 2110048692, stage 4), judged with the frame log's own motion measure (`frames.json`, the share of frames off even by over 4 ms, "strays", and the longest stretch off in a row).

**The PC is noisy.** The owner's i7-8550U laptop chip (4 cores, 8 threads) ran other test runs (Sunset Racer 2) at the same time, and runs of the same build swing by 2x. Every before/after is therefore an interleaved A/B: the two builds or settings take turns, several rounds each, and the A/B is judged on the spread, not one pair.

## Goals / Non-Goals

**Goals:**
- None of the four flags of the 07:14 live run: no freeze in the race, no hitch at the countdown, races moving evenly at both limits, 250 fps or more with no limit.
- Races exactly as they are: every recorded race plays out tick for tick as before (`test\verify-races.ps1`, also with `-Rollback 50`), golden frames unchanged.
- No input lag added, no check loosened, `test\perf.ps1`'s baseline untouched.

**Non-Goals:**
- Changing the race's own code or how often it ticks, even where a cost sits there (see Risks).
- New settings or options: everything here is on for everyone.

## Decisions

### 1. Field access through VarHandles (`FieldSlot`)

- The run-ahead captures and restores about 1,600 fields a tick (`StateCopy`, `RaceSnapshot`). Through `Field.get`/`Field.set`, Java 18 and later reads each field through a method handle of its own and, after 127 uses, spins a class for it ("customizing" the handle). All 1,600 reached that count in the same tick, about 1.1-1.5 s into the first race: 184-248 ms.
- `FieldSlot` holds a `VarHandle` per field, made once through `MethodHandles.privateLookupIn`, and calls it with the field's exact type (`(int) handle.get(o)`), which Java links straight to the field and never customizes. Primitive values travel as raw bits in a `long` (floats and doubles by their bit patterns), so nothing is boxed.
- The same field lists in the same order, read and written the same way: the copy and the replay's hashes come out bit for bit as before.
- *Alternatives:* `-Djdk.reflect.useDirectMethodHandle=false` (removed in Java 22); `Unsafe` field offsets (deprecated for removal, and its warnings would reach the owner's console); generating copy code per class (much more code for the same result).
- Also moved: `RaceState` (the replay recorder reads its fields every tick in real play; the live test records no replays, so it never saw this) and `PlayerHud` (split screen swaps the HUD's fields every frame).

### 2. Warm-up while the music loads, the rest in spare time

- **Why at all.** The first race's code is cold: Java interprets it, then compiles it in steps. For about two seconds a tick took 18 ms and a run-ahead 28 ms, against 11 and 12 later; with the kept scene and the card on top, the game thread needed more than the 53 ms a tick has, and frames stood still.
- **What.** `playAndPutBack` (shared with the run-ahead) plays the race's next tick and puts the race back exactly; the warm-up calls it 96 times, about as many ticks as the first two seconds of a race run, once a run of the game. And once a stage it records the countdown's first scene and has the card draw it unseen behind the next picture shown, so the card has its buffers, targets and shaders when the countdown starts.
- **When.** The race state is complete only from `SELECTEDCARSAVE` on, so warm-up ticks can run from `PREGAMEMUSIC`. The first, slowest ticks run while the music loads, up to 500 ms on top of it, once a run (the screen holds still then anyway: the stage picture with "Loading"; 96 ticks took 434-967 ms live, 500-510 ms in quiet hidden runs). The rest run in measured spare time on the screen before the race: before sleeping until the next tick, a warm-up tick runs only if the last one, plus a quarter, fits before the next tick is due less 6 ms. No frame or tick waits for one.
- **Never in split screen** (its second camera and HUD are not put back by `playAndPutBack`), **and never in the countdown or a race** (only `PREGAME`). The first version also played them in the countdown's spare time, with 200 ms while the music loaded: the live run at 120 fps played 54 of the 96 in the countdown, and a quiet hidden run 51, where one that ran long (code Java had not compiled yet) made the next tick 17-42 ms late and the motion jump 43 ms. The longer time while the music loads makes up for it: the autotest, which leaves the screen before the race after 0.7-0.9 s, had every tick played before the countdown in both quiet hidden runs.
- **Safety.** Under `verify-races.ps1 -Rollback` every warm-up tick is played and the whole race state compared before and after (`RaceSnapshot.captureComplete`); any difference fails the verify.
- *Alternatives tried:* the warm-up in the stage screen's ticks with a time slice (v1): its first cold tick took 108 ms and pregame frames 56-168 ms, so menus hitched; all 96 ticks in one block in `PREGAME`: smooth races, but a 1.1-1.3 s frame on the stage screen.

### 3. `-XX:+DisableExplicitGC`

- The original calls `System.gc()` on Enter at the stage screen (`musicomp`) and while loading the music (`RadicalMod`). With ZGC each call blocks its caller until a whole collection ends: 61-157 ms, the last right before the countdown's first tick; menus also showed 520 ms frames when one fell on a busy moment.
- ZGC collects on its own, concurrently, keeping under the 512 MB soft limit, so the calls are not needed. With the option the heap stayed under 452 MB and the number of collections was about the same.
- In `build.ps1`'s jlink `--add-options`; the runtime is rebuilt once, as its options' stamp changes.
- *Alternative:* removing the calls from the original's code: two places, and any other library call would still block.

### 4. The portrait tint at "3" reads only what is behind the portrait

- At `starcnt == 36` the original blends the player's portrait with the picture behind it (`blendude`), reading the back buffer. With the GPU renderer the back buffer is stale, so the whole frame was drawn again in software first (`syncBackBuffer`, 45 ms or more) and the blend went through `PixelGrabber` and `Color` objects (about 25 ms): 67-137 ms in that tick.
- Now `syncBackBuffer(region)` draws only `PORTRAIT_BEHIND` (217-453 x 0-160, both places the portrait can go, in the back buffer's pixels): the clip is set in device space, and `SceneRecorder.replayCommands` skips a polygon whose bounds miss the clip (grown by 3 device pixels for antialiasing and lines). The back buffer stays marked stale, so the next whole sync still draws the rest.
- The portrait's own pixels are decoded once while the music loads (`readPortraits`), and the blend is integer arithmetic: `(portrait + 3 × behind) / 4` per channel, as `Color`'s did.
- *Checked:* a temporary comparison of the clipped sync against a whole sync, both in the same tick: 0 of 37,760 pixels differed.
- *Alternative:* read the pixels back from the card. That would wait for the card mid-frame and is a new path for one tick a race.

### 5. Carry-on 0.5 of a tick

- Between ticks, frames place the cars along the last tick's motion; past its end they carry it on for at most `MAX_CARRY_ON` of a tick, then stand still until the next poses come. At 0.25 (13 ms), any tick that took more than 13 ms to reach the presenter made frames stand still and then jump.
- The previous change (no-frame-limit-stutter) kept 0.25 after an A/B of two runs each that showed no clear difference. This time, with the tick trace and three variants: race strays 2.9-3.3% at 0.5 against 4.9-8.7% at 0.25, and the corrections when the poses came (median of the runs' medians) 6 units against 15. Carrying on further means fewer frames stand still, and the correction, when it comes, is from a closer guess.
- **Input lag.** Unchanged by construction: new poses are used the moment they are handed over, whatever the carry-on; it only decides what frames show while none have come. The `[draw]` line's "key to screen" counts from the key to the first frame showing its effect, which the carry-on never delays.

### 6. The replay recorder walks the names once

- At the countdown (`countdownStarting`) the recorder took the start state, the start state's names and the layout, which walked the names again: 125 ms at "3". The layout now folds the names already made (`RaceState.layout(view, names)`), giving the same hash.

### 7. The effect classes initialized with `Plane`

- About 1.7 s into the race, in about half the runs, two or three ticks took 50-100 ms each (the race step, the run-ahead and the kept scene alike), always in `Plane.d`, the polygon drawing.
- The JIT log showed why: `Plane.d ... trap_bci=3206 uninitialized reinterpret`, then `made not entrant: uncommon trap`. Bytecode 3206 reads `EffectTrails.on`, on the path for flying debris. Java compiles `Plane.d` fully while the menus draw cars; when it finishes before the countdown's first scene has initialized `EffectTrails`, the compiled method holds a trap there, and the first chip of debris throws the whole 7.6 KB method away while it is compiled again. In the runs where the compile finished after the countdown began, there was no stall.
- `Plane`'s static initializer now initializes `EffectTrails` and `Glow` (the other class `d()` only reaches on rare paths). Neither has anything to set up that a race sees.
- No JVM option avoids it: the trap limits the runtime already sets (`-XX:PerMethodTrapLimit=0`) do not cover a class that is not initialized. *Alternative:* initializing them in the game's start-up code; the reason is `Plane.d`'s, so the fix sits next to it.

### 8. Polygons that cross themselves cut in bands for the card too

- **Why.** The countdown stayed under 250 fps (216 at 07:14) though its ticks were lighter than the race's (half within 32 ms against 40, quiet PC): the presenter was slower, not the game thread. The `[draw]` line: a countdown scene had 216-387 draw calls, 45-59 thousand vertices and 114-204 polygons filled through the stencil; a race scene 130-160, 25-30 thousand and 70-86. Handing the card a frame took 5.3 ms against 4.3. Each stencil polygon is two draw calls with a stencil state of their own and ends the batch of plain polygons before it, so 200 of them make about 600 submits.
- **Which polygons.** A temporary count in hidden runs: of the polygons that are not convex, ear cutting handled about 87%. The rest crossed themselves (about 75% of them: faces seen edge-on, track pieces near the camera whose far corners land thousands of pixels off the screen) or touched themselves (about 25%: the wheels, rings drawn as one outline that goes round twice). 140-200 a countdown scene, 60-90 in a race, a replay or a highlight.
- **What.** `SceneGeometry.bandFill`, which split screen's drawing on the processor already used, also runs when a kept scene is built for the card (`cutLines`, `bandPieces`): the polygon is cut across at every corner's and crossing's height, and its inside in each band lies between the first and second edge from the left, the third and fourth and so on. A point where a cut meets an edge is a vertex of a new role (`ROLE_ALONG`): the edge's two corners and the share of the way along it, which `Shaders.PROJECTED_VS` places each frame, so the point stays on the edge while the corners move until the next tick.
- **No cracks.** The first version cut each band piece at just its two edges' points. A corner of the next band lying between them then came off the cut as the corners moved, and the projection test caught a one-pixel crack across the screen in one of 60 frames (a road piece near the camera). Now each piece runs along its top and bottom cuts through every point on them between its edges, in one order per cut (left to right, ties by point number), so a piece and its neighbours across a cut share the same points and meet exactly. Both pieces' share of a point is worked out from the cut's height alone. Where two edges cross, the crossing was placed on each edge on its own, so the two drifted apart as the corners moved; now both go where the edges cross in each frame (decision 15).
- **Flat polygons keep the stencil.** A polygon whose corners all lie at one height when it is cut has no band, yet may have a pixel of height a frame later; the stencil fills it from its corners in each frame. 0-3 a scene.
- **What it costs the game thread.** A band polygon is about seven times the vertices of its fan, so building a countdown scene for the card took 1-5 ms longer a tick (busy PC; the race's scenes about the same as before). The cleanup pass cut the work around those vertices: the pairs of a polygon's edges are looked at once, for both the ear cutter's "does it touch itself" and the heights where edges cross (`scanEdges`; the two took a pass each), a band takes the edges across it from its top cut's own points instead of from every edge (`edgesFromCut`), and each cut point's share along its edge is worked out once. A temporary check built every scene both ways, with the committed code and the new, in the same hidden runs, alternating which went first: the same bytes in 1,000+ scenes for the card and 3,800 placed on the processor (`-Dnfm.retained=false`), and the countdown's scenes built in 6.5 ms against 7.1, the processor's in 1.68 against 1.69.
- *Checked:* the projection test (`-Dnfm.projectiontest=60`, the same frame placed on the processor, where bands are cut every frame, and on the card; pixels compared): median 0.0009% and 0.0020% of the picture, worst 0.0091% and 0.0129%, against 0.0009-0.0011% and 0.0100-0.0103% before. Draw calls a scene: 1-3 (9 with flat polygons) against 130-387. Vertices up about a fifth.
- *Alternatives:* batching the stencil polygons (only those that do not overlap could share a pass, and painter's order decides which); cutting the bands on the presenter each frame (an upload of its own every frame, and still separate draws).

### 9. A race's frames are timed from its first scene

- **Why.** The race's first scene takes 60-90 ms to make (the countdown's camera sees most of the track; quiet hidden runs: kept scene 28-47 ms, the card's part 33-44 ms), while the screen before stays up. Its frames were timed from when the menu tick that started the race was due: the first frame showed the race 79 ms behind, frames stood at the end of a stretch already gone by, and ticks 1 and 2 ran 28-85 ms late to catch up, each with its scene. Live: "the race stood still or jumped" for 152 ms (no limit) and 118 ms (120 fps) at 0.1 s, in every run before this change too (06:27 and 07:14).
- **What.** `handOverKept` knows a race's first scene by the frame before it not being a race's (decision 14): that scene's stretch starts when it is handed over and lasts a race tick (the tick that started it was the menu's, 40 ms), and the run loop has the next tick due one tick later. It applies wherever a race's frames follow a menu's: the countdown, and a race, replay or highlight after a menu.
- **Races.** The same ticks with the same keys: only their moment on the clock moves, once, by the first scene's 60-90 ms, while the screen before is still up. Recorded races (`verify-races.ps1`) never use the presenter.
- **Result** (quiet hidden runs, seed 2110048692): tick 1 began 0.0-0.1 ms late against 28-85 ms, and the first frames move from the first one on.

### 10. Frames placed for the moment they reach the screen

- **Why.** At 120 fps one frame in eight of the countdown was off even by over 4 ms (live 78 of 759, quiet hidden 82 of 793), spread evenly over it. The frames CSV against the tick trace showed which: once a tick, the first frame with the new kept scene took 12-14 ms instead of 8.3 and showed the race 4-6.7 ms behind the screen against 0.7 for the others. That frame sends the card the scene (1-3 MB) and the HUD, and it was placed for the moment it started.
- **What.** The presenter keeps how long a frame takes from being placed to reaching the screen, smoothed, apart for frames that send the card a new scene (a quarter of each new measure) and the others (a sixteenth), capped at 16 ms so a stall does not throw the next frames off, and places each frame for that moment.
- **Input lag.** New poses are used the moment they come, as before; a frame shows the race at the moment it reaches the screen instead of 1-6 ms before it.
- **Result** (quiet hidden runs): the countdown at 120 fps 14 of 815 frames off even by over 4 ms (1.7%), against 82 of 793; with no limit 8 of 1,921 against 125 of 1,616; the race at 120 fps 1 of 2,300.
- *Alternatives:* sending the card the next scene a frame early (the frame before it then takes the time instead); letting frames queue on the card (input lag).
- **By place after a new scene** (12febb0). In split screen the card gets two panes' scenes at once, and the two frames after the one that sends them waited 3-5 ms more on the card still busy with it (`bgfx_frame` holds at most one frame queued): they showed the race +3.1 and +2.7 ms behind against -1.5 for the rest, 71 of the 75 frames off even by over 4 ms in a split countdown at 120 fps. The presenter now keeps the time apart by the frame's place after a new kept scene: the frame that sends it, the two after it, and the rest (a quarter of each new measure for the first three, a sixteenth for the rest). One player is as before: there those two frames were on time.

### 11. The warm-up's scene drawn as a race frame draws it, in split screen too

- **Why.** The countdown's third frame took 30-48 ms in every quiet hidden run. Sampled on the presenter thread, all of it is in `bgfx_frame`: bgfx works on the calling thread with at most one frame queued, so the third frame's swap waits for the card to finish the first two. The warm-up's unseen draw (decision 2) had the scene's buffers, target and shaders ready, but drew no HUD: the countdown's first frame was the first to make the HUD's texture (the picture's size, 1920x1080) and draw it with its blend. Split screen had no warm-up draw at all (the live test: the card held its first countdown frame up 101 ms).
- **What.** The warm-up scene keeps the HUD layer as it stands and is drawn with it, where a race frame puts it, and with the start's white flash; in split screen both panes are recorded and drawn as their frames do (`SplitRace.inPicture`). Split screen's ticks are still never played ahead.
- **Result** (interleaved quiet hidden runs, no AOT cache on either side): the third frame 30-34 ms against 38-48 ms in 3 of 3 pairs. Not all of it: with frames slowed down by a trace (one line printed a frame) the stall did not come at all, and the card's own time for those frames was 0.3-4.9 ms, so the rest is the swap's wait on Windows' and the driver's side, not the card drawing.

### 12. A split-screen pane replays inside the clip it is given

- **Why.** Every split countdown had one tick of 54-78 ms (against 20-30), 4.95 s in, and the next tick late 13-25 ms: the tick that tints the countdown portrait with the picture behind it (decision 4). It redraws only the portrait's part of the picture in software, by clip; `SceneRecorder` replaced the clip with each pane's own at the pane's mark, so both panes were redrawn whole.
- **What.** A pane's clip is put inside the clip the replay was given. Every other replay gives no clip or the whole picture, where this draws the same pixels as before.

### 13. The greyed race behind the pause menu and split results read from the picture's buffer

- **Why.** Split screen's results' first tick took 56-98 ms against a 40 ms menu tick, so the results stood still 115-150 ms as they came up; the pause menu's first, 42-48 ms. About half of it was the `PixelGrabber` reading the 1920x1080 picture, cold every time (it runs once a race), and the greying through two `Color` objects a pixel.
- **What.** A `TYPE_INT_RGB` picture is read with `Raster.getDataElements`, any other with `getRGB` (the grabber stays for an image that is not a buffer), and greyed with whole numbers. The same pixels: the readers take only red, green and blue. The end-of-race fade and car select read their picture the same way.
- **Result.** The first greying in a run 59 → 20 ms, warm 9.6 → 6.7 ms (scratch harness, all pixels the same on display-compatible, ARGB and byte pictures). In the game with its AOT cache (interleaved hidden split-screen runs, two each, every results screen in them, beside another game using the processor): the results' longest frame, median 200 → 89 ms (126-264 against 67-133).
- *Left:* the race replayed in software into the picture first (15-35 ms in split screen): the grey must be of the race as it ended.

### 14. A race's first scene is one after a menu's frame, not any presenter restart

- **Why.** The blind review of ddc18c0 (finding 1): decision 9 took a race's first scene to be any scene handed over while the presenter drew nothing, and the presenter also stops for a single frame in the middle of a race: a screenshot (the live test takes one every 10 s), or a scene that could not be recorded. The scene after it then moved the tick clock, the next tick due a whole tick after it was handed over: up to a tick late once, and a key pressed then could land in the next tick.
- **What.** The game thread notes whether the last frame shown was a race's, the presenter's or one it drew itself (`raceOnScreen`); a scene is a race's first only after a frame that was not. The presenter starting again after a frame drawn in software carries on with the ticks' own times.
- **Result.** A hidden run with screenshots on (about 90 in the race, each stopping the presenter for a frame): the race's 1,999 ticks all came due 53 ms apart, none moved. Races: `verify-races.ps1` 20 matched (they never use the presenter).

### 15. Where two edges cross, both bands' points go where they cross in each frame

- **Why.** The blind review of ddc18c0 (finding 2): a crossing has a point on each of its two edges, placed as shares of the way along them (decision 8). As the corners move the edges cross elsewhere, the two points drift apart, and the pieces either side fill past the outline or leave a sliver. Measured on the game's own polygons that cross themselves (1,425 of them in twelve `-Dnfm.motiontest` scenes, each cut where it is halfway between two ticks and placed for the 48 other moments it was drawn at, 67,345 placements; pixel centres against the even-odd fill): 1,775 pixels wrong, the worst placement 126.
- **What.** Both points are a vertex of a new role (`ROLE_CROSS`): the four corners of the two edges, and the shader places it where the edges cross in that frame. It stays on the first edge between where that edge meets the cuts above and below, so the crossing of two edges that are almost parallel, which slides a long way as they move, cannot fold the pieces either side; a crossing that would leave them sends its polygon to the stencil instead (decision 16). The four corners go in the four point numbers a vertex has, which needs each corner's x and y to come from one point (all the recording's corners); a polygon with one that does not goes to the stencil too.
- **Result.** The same placements: 135 pixels wrong, the worst 17 (a polygon that turns to nothing, the same before); better in 108, worse in 13, by a pixel each. Random polygons with a corner moved by 0.5 px: 0.106% of the inside wrong → 0.011%; tilted as by perspective: 0.046% → 0.001%. Corners moved apart at random by 2 px and more, far beyond what a tick does, keep about the same share wrong, the worst polygon worse.
- *Alternatives:* keeping the stencil for every polygon that crosses itself (back to 400-600 draw calls a countdown scene, decision 8); clamping nothing (the crossing of nearly parallel edges then folds the pieces: worse on random polygons, the game's own 139 pixels against 135).

### 16. A polygon whose bands would not hold until the next tick goes to the stencil

- **Why.** The blind review of 1098c71 (finding 1): decision 15 keeps a crossing between where its first edge meets the cuts either side. Once the edges cross outside that band, the point the pieces either side share comes off the second edge, and they leave a hole or fold over each other; edges that start or stop crossing within a tick are not in the bands at all. Measured (`test\geometry-check.ps1`): of the game's 1,425 polygons that cross themselves, 26 had a crossing leave its band between two ticks; random polygons with one edge moved 2 px down, the review's own check, had 0.50% of their inside wrong. Counting what is filled outside and what is missed inside apart also showed that a piece convex where it is cut can fold as its corners move: a long thin piece whose side lies almost along a cut, as its corner moves a pixel across it, and a piece with the tip of a notch on its cut, as the tip moves into it.
- **What.** A kept scene's frames are placed from its tick's moment to half a tick past the next (`PoseSpan.MAX_CARRY_ON`). When it is made ready for the card, the scene's own placing gives the corners at both ends (`ScenePoints.probe`, `RetainedScene.Probe`), and `SceneGeometry.bandsHold` keeps a polygon's bands only if, at both, the same edges cross, each crossing stays within its band on both its edges, every crossing is one the card places where the edges cross (`ROLE_CROSS`), and no triangle of a piece turns over. Each piece now goes as a strip of triangles that each have points on both its cuts: a fan from its first point had triangles along its top that were flat where it was cut, and which way such a triangle turns says nothing. A polygon that fails is filled with the stencil from its corners in each frame, exact wherever they go.
- **Why that is enough.** While the same edges cross where the card places the crossings, the pieces' outlines are the polygon's even-odd outline, cut along points they share; triangles that all keep their turn then cover every point inside once and none outside.
- **Result.** The game's polygons (the same twelve scenes, each placed for the moments it was drawn at): 106 pixels wrong of 21.8 million inside, every one a pixel centre within 0.0001 px of the outline, a tie between the triangles' edges and the even-odd rule's in the check itself; before, 135, 28 of them off the outline, the worst placement 17. 119 of the 1,425 polygons (6-16 a scene) go to the stencil: 12-32 more draw calls a scene, against the 400-600 decision 8 took out. Random polygons, 2,000 a case (px² wrong, at samples every half pixel): an edge moved 2 px 8,744 → 0.3; one corner by 0.5 px 208 → 0, by 2 px 2,756 → 0.3; every corner by 0.5 px 2,406 → 0, by 2 px 29,044 → 0.5, by 5 px 130,810 → 0; tilted by 1 px 112 → 0.3; what is left is samples on the outline. The check costs about 3 µs a polygon that crosses itself, 0.3-0.35 ms a scene, once a tick on the game thread.
- *Alternatives:* the stencil for every polygon that crosses itself (decision 8's draw calls back); a limit worked out where the polygon is cut, how far an edge may move before a crossing leaves its band (below a quarter pixel already 43% of the game's polygons, and folds it cannot see left pixels wrong); checking each frame on the presenter (bands cut again there, decision 8's alternatives). Checked at the ends, a polygon whose bands turn over and back within a tick would be missed: none in the measured scenes.

### 250+ fps and no stutter

Not measured on this build yet: the live test (`test\live.ps1`, one player and split screen, no limit and 120 fps) and the performance gate need a quiet PC with the display on, and the PC is in use (23 Nov). ### Races stay identical

- No race code changes. The warm-up and run-ahead put the race back through the same copy as before; the copy reads and writes the same fields with the same values.

## Risks / Trade-offs

- **Other classes compiled before they are ready.** The same kind of trap was seen once more, in `GameUi.statPlayer` at its first "wasted" message (a string joined for the first time), with no slow tick around it. Only `Plane.d` is large and hot enough for its recompile to show.
- **Stalls from a busy PC.** In hidden runs while other test runs loaded the processor, some ticks began 100-400 ms late with no collection, compile or trap anywhere near: the game thread simply did not get the processor. The live test waits for a quiet PC.
- **The countdown is the heaviest part.** Its camera sees most of the track: the kept scene takes 13-22 ms and the card's part 7-11 ms (1-5 ms more with the bands, decision 8), against 8 and 4 in the race. On a quiet PC a tick fits in 53 ms (half within 32 ms); when other programs load the processor it does not, and ticks are handed over late.
- **Warm-up costs up to 500 ms more on the loading screen**, once a run of the game (500-510 ms in quiet hidden runs). The screen holds still then anyway. A player who leaves the screen before the race very fast can start a race with a few warm-up ticks unplayed; the countdown does not make them up.
- **A race starts 60-90 ms later after Enter** than the tick clock alone would have it (decision 9): the screen before stays up while the first scene is made, as it did before; only the race's clock now starts with the first frame.
- **The frame rate with no limit.** The presenter is bound by handing frames to the card (`bgfx_frame`, one frame in flight); decision 8 takes most of the draw calls out of it. Letting more frames queue would raise the frame rate and add input lag, which the owner forbids.
- **Bands placed on the card are a tick's guess.** Between ticks the cut points move along their edges rather than staying at their height; the outline is always exact, the cuts inside it are not horizontal any more, which nobody sees as the piece has one colour.
