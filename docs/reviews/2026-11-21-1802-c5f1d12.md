### high: An incomplete live run can pass without reaching a race

`test/live.ps1` lines 82-99, confidence 0.99

The wrapper accepts any run that writes frames.json and grades only the parts present. The split autotest writes that file and exits 0 even when it times out in a menu. A broken path into a split race can therefore pass without measuring its countdown, race, or replay. Parts with fewer than 10 frames are also silently skipped.

Recommendation: Require an explicit completion result and sufficient frame samples for every required phase. Return a nonzero status when a requested run times out, misses a phase, or has too few samples.

### high: The 250 fps gate can pass when the report shows 240 fps

`test/live.ps1` lines 135-143, confidence 0.98

The floor uses fps recalculated after subtracting graphics-card holds, while the report prints the original fps. For example, 960 frames over four seconds with a 200 ms hold become about 253 fps for the gate. The same hold can downgrade the hitch to a note, so the run can exit 0 despite reporting 240 fps and a 200 ms interruption.

Recommendation: Apply the floor to the displayed-frame rate in the report. Keep adjusted fps as a diagnostic, and mark a run inconclusive when off-screen presentation prevents a reliable measurement.

### high: The GPU check misses CPU-rendered frames presented by the card

`openspec/specs/performance/spec.md` lines 37-42, confidence 0.99

The new check promises to verify GPU drawing for the game, menus, and race views. It only rejects race parts labeled software. GameSparker.java records a CPU-rendered back buffer uploaded to the GPU as picture, including when GPU scene drawing fails and syncBackBuffer supplies the frame. That fallback can pass, and CPU-rendered menus are outside the check entirely.

Recommendation: Make the test distinguish GPU drawing from GPU presentation, verify both menus and race views, and flag CPU drawing whenever the GPU is available.
